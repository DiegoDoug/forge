## 1. Screens / views

One screen, one new route:

- **`/model-playground`** — single page with two areas:
  - **Providers** (top): a compact list of the two supported providers (OpenAI, Anthropic — per ADR-0011). Each row shows the provider name, whether a credential is configured, and an action to configure/replace/remove its key.
  - **Playground** (main area): a prompt composer (textarea + provider/model checkboxes, limited to configured providers) above a grid of result panels, one per selected provider/model, plus a collapsible history list of past runs.

No second screen — history is a panel within this page (a list the user can expand/select from), not a separate route, since a run is only ever meaningful in the context of re-running or comparing against a new prompt.

## 2. Navigation

`frontend/lib/nav-registry.ts` gains one entry, added after `Prompt Studio` (keeps the two LLM-adjacent features adjacent in the sidebar and command palette):

```ts
{ title: "Model Playground", href: "/model-playground", icon: FlaskConical, description: "Compare LLM provider outputs side by side" },
```

- `FlaskConical` (lucide-react) is unused elsewhere in the registry and reads as "experimentation" without colliding with `MessageSquareText` (Prompt Studio) or `Sparkles` (Project Init).
- No keyboard shortcut assigned in v1 — all single-letter shortcuts already listed in the registry are taken (D, V, N, G, C, O, U, `,`); assigning one isn't required by [`04_UI_GUIDELINES.md`](../../04_UI_GUIDELINES.md) §2 (only sidebar + palette reachability is), so this is deferred rather than forcing a two-letter shortcut nobody asked for.
- The command palette (`cmdk`) reads the same `NAV_ITEMS` registry, so this one change covers both surfaces.

## 3. States

**Providers list**
- Empty (no credentials configured anywhere): both providers shown, both greyed out with a "Configure a key" action — never fully invisible (resolves [`01_SPEC.md`](01_SPEC.md) §6's non-blocking open question in favor of discoverability over hiding).
- Loading: `Skeleton` rows while `GET /api/model-playground/providers` is in flight.
- Error: inline retry affordance (reuses `EmptyState`'s error variant if available, otherwise an inline `Alert`) — this is a background metadata fetch, not a blocking error for the whole page.
- Populated: provider row shows label + "Replace key" / "Remove key" actions once configured.

**Prompt composer**
- Disabled submit state with a hint ("Configure at least one provider to run a comparison") when zero providers are configured — this is the composer's own empty state, distinct from the providers list's.
- Provider/model checkboxes only list configured providers' models; nothing to select when none are configured.

**Result panels (per run)**
- Loading: each panel shows its own `Skeleton` independently — panels do not wait for each other (per spec FR7).
- Success (populated): response text, model id, latency, token usage if reported.
- Error: user-legible message (e.g. "Request failed" / provider-reported error text), a retry-this-panel action, never a raw stack trace.
- Timeout: distinct from a generic error — explicit "Timed out after 60s" message (per spec FR9).

**History list**
- Empty: `EmptyState` — "No runs yet" with the composer as the implied first action (no separate CTA needed; the composer is already on the same page).
- Loading: `Skeleton` rows.
- Populated: prompt excerpt (truncated), provider/model badges, relative timestamp (`date-fns`), per-row delete action.

(All per [`../../04_UI_GUIDELINES.md`](../../04_UI_GUIDELINES.md) §5.)

## 4. Responsive behavior

- Result panels lay out as a responsive grid (`md:grid-cols-2`/`lg:grid-cols-3` depending on panel count, capped — see §6 API's target-count cap in `06_API.md`), collapsing to a single column below `md`, matching the existing Converters grid pattern (`02_UI.md` precedent from Phase 04).
- The providers list and history list are already narrow, list-shaped content — no responsive redesign needed, single column at every width.
- Prompt composer textarea and provider checkboxes stack vertically below `md`.

## 5. Accessibility

- Provider/model checkboxes are real `Checkbox` components (keyboard-toggleable, per existing shadcn primitive), not custom click targets.
- "Configure key" / "Replace key" / "Remove key" actions are reachable via Tab and activate on Enter/Space (standard `Button`/`Dialog` behavior — no custom interaction pattern introduced).
- Result panel retry actions and history delete actions are keyboard-reachable buttons, not icon-only click zones without a label (each gets an `aria-label` or visible text).
- No drag-and-drop, no canvas/custom-input surface — this phase introduces no new accessibility pattern beyond what shadcn/ui primitives already provide.
