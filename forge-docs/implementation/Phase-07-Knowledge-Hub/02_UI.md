## 1. Screens / views

### 1.1 Knowledge Hub — `/knowledge` (new)

The only new page. Layout, top to bottom:

- **Header** — title, and a live count ("137 items", or "12 of 137 shown" when filtered).
- **Filter bar** — a text query input, a type selector (All / Notes / Documents), a tag multi-select, and a project selector. Filters compose (`01_SPEC.md` FR6) and are reflected in the URL as query params so a filtered view is linkable and survives a refresh.
- **Result list** — one row per item showing a type badge, title, excerpt, tag chips, project chip, and relative updated-at. Rows are keyboard-focusable and activate on Enter.
- **Truncation notice** — when the API returns `truncated: true`, an explicit "Showing the first 100 of N — narrow your filters" line (the cap is always 100; only `N`, the true total, varies). Never a silent cut (`01_PRODUCT_PRINCIPLES.md` §1.3, `01_SPEC.md` §6.6). There is no "load more" or "next page" control — this phase has no pagination.

Selecting a row navigates to the owning feature (`01_SPEC.md` FR7): `/notes` for a Note, `/documents` for a Document.

> **Verified repo constraint — neither feature has a per-item route today.** `frontend/app/(app)/notes/` and `frontend/app/(app)/documents/` are each a single `page.tsx`; Documents selects the active document inside the page (via `document-sidebar.tsx`), and the Notes board is a free-positioned canvas. There is no `/documents/[id]` and no per-note URL.
>
> Phase 07 therefore ships **navigate-to-feature**, not deep-link-to-item: clicking a result lands the user on the right page, and highlighting or selecting the specific item is best-effort via a query param (e.g. `/documents?doc=<id>`) **only if** the existing page can honor it without restructuring. Adding real per-item routes to two shipped features is a change to those features, which `01_SPEC.md` §5 puts out of scope. If the query-param approach turns out to require restructuring either page, drop it and navigate to the bare route — do not invent routes.

### 1.2 Tag and link editing surfaces (modified views)

Tagging and linking are edits to an item, so they belong where the item is edited — not on the Hub:

- **Document editor (`/documents`)** — gains a tags control and a "Linked items" section in the existing `document-sidebar.tsx`.
- **Note card (`/notes`)** — gains tag chips and a tag/link affordance in the existing note card or its expanded state.

The Hub itself is **read-and-navigate**; it displays tags but does not edit them. This keeps the Hub from becoming a third editor (`01_SPEC.md` §5) and puts each control next to the content it describes.

> **Design note, needs confirmation at T7/T8:** the Notes board is a free-positioned canvas of cards (`notes-board.tsx`, with `pos_x`/`pos_y`/`z_index`), not a list. Where a tag/link control fits on a sticky-note card without crowding it is a real design question. If it does not fit cleanly, the fallback is a per-note detail popover rather than cramming controls onto the card face.

## 2. Navigation

Per `04_UI_GUIDELINES.md` §2, the Hub must be reachable from both:

- **Sidebar** — a new entry in `frontend/lib/nav-registry.ts`. Proposed: title "Knowledge", href `/knowledge`, icon `Library` or `BookOpen` (lucide-react, already a dependency), description "Search, tag & link notes and documents". Shortcut letter to be picked from the unused set — `K` is proposed (unused today; `D`, `V`, `N`, `P`, `G`, `C`, `O`, `U`, `,` are taken).
- **Command palette** — automatic, since the palette is driven by `NAV_ITEMS`.

`/search` keeps its current behavior and its absence from `NAV_ITEMS` — this phase does not change it (`01_SPEC.md` FR21).

## 3. States

For `/knowledge`:

- [ ] **Empty — no knowledge at all.** "No notes or documents yet" with calls to action linking to Notes and Documents. Distinct from the filtered-empty state.
- [ ] **Empty — no matches for these filters.** "No items match these filters" with a "Clear filters" action. Distinct from the above (`01_SPEC.md` FR8).
- [ ] **Loading.** Skeleton rows, matching the convention used by the Projects and Secrets lists.
- [ ] **Error.** Message plus a retry action, matching existing list-error patterns.
- [ ] **Populated.** The result list, plus the truncation notice when applicable.

For the tag control: loading, empty (no tags yet, with inline create), populated, and a duplicate-name resolution that reuses the existing tag rather than erroring (`01_SPEC.md` FR10).

For the linked-items section: empty ("No linked items"), populated, and the two error cases from `06_API.md` §3 (self-link, duplicate link) surfaced as inline validation, not toasts that vanish.

Required by `04_UI_GUIDELINES.md` §5.

## 4. Responsive behavior

`04_UI_GUIDELINES.md` §3 explicitly names "future Knowledge Hub search results" as a data-dense view needing a real mobile layout, not a squeezed desktop table.

- **Desktop** — filter bar horizontal; result rows show every field.
- **Mobile** — filter bar collapses into a filter sheet/disclosure; result rows become stacked cards (title, type badge, excerpt clamped to two lines, tags wrapped); the truncation notice stays visible.
- The result list is never a horizontally-scrolling table at any width.

## 5. Accessibility

- [ ] Every filter control is reachable and operable by keyboard alone, with visible focus.
- [ ] The tag multi-select is a real listbox/combobox with correct roles and `aria-multiselectable`, not a div soup — reuse the existing shared select/combobox primitive where possible.
- [ ] Result rows are focusable and activate on Enter/Space; the whole row is one target, not a nest of competing tab stops.
- [ ] The result count and truncation notice live in an `aria-live="polite"` region so filtering announces its outcome to a screen reader.
- [ ] Tag chips have accessible remove buttons with names like "Remove tag client-a", not bare icon buttons.
- [ ] Light and dark theme both verified.

> **Known repo caveat to watch:** Phase 06's post-implementation review records that the shared `components/ui/select.tsx` wrapper renders raw item values rather than labels (a Base UI `Select.Value` characteristic), and that new consumers need the children-as-function workaround. The Hub's type/project/tag pickers are exactly such new consumers. Fixing the shared wrapper itself remains out of scope here, as it was in Phase 06 — but the workaround must be applied deliberately, not rediscovered.
