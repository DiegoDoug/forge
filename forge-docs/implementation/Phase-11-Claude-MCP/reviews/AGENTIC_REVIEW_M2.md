## 2. Findings (as of the initial pass — see §5 for current/fixed status)

### BLOCKER — FIXED, see §5

**B1 — The `confirm: true` "structural only, never inferred" guarantee is not actually enforced; type coercion lets non-boolean truthy values through.**

- **Files:** `backend/app/mcp/tools/notes.py::forge_delete_note` (line 66), `backend/app/mcp/tools/documents.py::forge_delete_document` (line 66) — both declare `confirm: bool` with no `Literal[True]`/`const` constraint, and both gate on `if confirm is not True: raise AppError(...)`.
- **The design intent is explicit and repeated across three documents.** `01_SPEC.md` §6: *"`confirm` is a required field of type `const: true`... there is no code path where a handler could be tempted to 'interpret' intent, because malformed/absent confirmation never reaches handler code."* `06_API.md`: *"`confirm` is a required literal `true` (JSON Schema `const: true`); omission or `false` fails schema validation before the handler body runs at all."* `IMPLEMENT.md`'s Milestone 2 Execution Rules: *"`confirm: true` is structural only — a literal JSON field, `const: true`, required by the input schema itself; never inferred from any other signal."*
- **What's actually shipped diverges from all three.** The tool's advertised JSON Schema (confirmed by dumping the live `tools/list` response) is a plain `{"type": "boolean"}`, not `const: true`:
  ```json
  "confirm": { "title": "Confirm", "type": "boolean" }
  ```
  Validation is done by the MCP SDK's own `func_metadata.py` via a plain Pydantic `BaseModel.model_validate(...)` with no `strict=True` configured anywhere in `ArgModelBase`/`FuncMetadata`. Pydantic v2's default *lax* mode for a `bool` field accepts (and silently coerces) `"true"`, `"True"`, `"1"`, `"yes"`, and the integer `1` into Python `True` — none of which are the literal JSON boolean the spec demands.
- **Empirically verified, not just reasoned about.** Built a fresh app instance, created five notes, and called `forge_delete_note` against each with `confirm` set to `"true"`, `1`, `"1"`, `"True"`, and `"yes"` respectively. **All five deletes succeeded** (`isError: false`, `{"deleted": true, "id": ...}`), because by the time the handler's `if confirm is not True` check runs, Pydantic has already silently converted the input into the Python singleton `True`. Only an actually-omitted field or a literal `false` are rejected (confirmed both still work correctly).
- **Why this is a Blocker, not a Major.** This is exactly the failure class the spec calls out by name and asks to be defended against structurally: "no natural-language phrasing... can substitute for the literal structured field" (`08_ACCEPTANCE.md` AC8). A stringy/truthy value reaching the handler and being treated as confirmation is precisely that class of soft signal sneaking through — the code path the spec says must not exist, does exist. This is also directly reachable by any MCP client, not just Claude: anything that sends raw JSON-RPC to `/mcp` (a differently-behaved client SDK, an intermediary that stringifies tool arguments, a hand-crafted request) gets the same silent bypass. The mitigating factor is that a spec-compliant client following the advertised `{"type": "boolean"}` schema would normally emit a real JSON boolean and never trigger this — but the entire reason the spec insisted on `const: true` instead of plain `boolean` was to not depend on client good behavior for a destructive, irreversible, no-trash operation.
- **The existing test suite does not catch this.** `test_mcp_tools_crud.py`'s only confirm-related assertion is `confirm: False` (rejected) and `confirm: True` (accepted) plus the omitted case tested separately for `forge_delete_note` via a different script. `VERIFICATION_CONTRACT.md` checks AC8 `[x]` on the strength of that single sub-case; it does not cover type coercion at all, so the self-report's "AC8 satisfied" claim is broader than what was actually verified.
- **Suggested fix:** annotate the parameter as `confirm: Literal[True]` instead of `bool` (Pydantic's `Literal` validator does not apply the same lax boolean coercion — it requires an exact match against the literal set), or explicitly configure `strict=True` for this field via `Field(strict=True)`/`Annotated[bool, Field(strict=True)]` so the SDK's generated Pydantic model rejects non-bool types outright, and add a regression test asserting `confirm: "true"`/`confirm: 1`/`confirm: "yes"` are all rejected, not just `confirm: false`/omitted.

### MAJOR

**M1 — FIXED, see §5 — `forge_create_note`/`forge_update_note`/`forge_create_document`/`forge_update_document` do not return the documented "not found" error for an unknown `project_id`; a raw, unhandled database error leaks internals (and the user's just-submitted content) into the tool response instead.**

- **Files:** `backend/app/services/notes/service.py::create_note`, `backend/app/services/documents/service.py::create_document` (and the corresponding update functions) — none validate `project_id` against the `projects` table before insert/update; they rely entirely on SQLite's `FOREIGN KEY` constraint (confirmed enabled via `PRAGMA foreign_keys=ON` in `app/database/session.py`) to reject the write at commit time.
- **`06_API.md`'s explicit, specific contract for `forge_create_note`:** *"Unknown `project_id` → not-found error, not a silently-orphaned note."* Verified empirically: calling `forge_create_note` with `project_id: "does-not-exist"` does **not** produce a clean not-found error. It produces:
  ```
  Error executing tool forge_create_note: (sqlite3.IntegrityError) FOREIGN KEY constraint failed
  [SQL: INSERT INTO notes (id, title, content, color, project_id, ...) VALUES (?, ?, ?, ?, ?, ...)]
  [parameters: ('dfb5c68ceb7e4458a1dfbf8c10071b13', 'orphan test', '', '#fde68a', 'does-not-exist', ...)]
  (Background on this error at: https://sqlalche.me/e/20/gkpj)
  ```
  This leaks the raw SQL statement and every parameter value — including the note's title/content the caller just tried to save — straight into the MCP tool-error response, rather than the promised clean "not found" message.
- **The one thing that *is* correctly preserved:** the FK constraint does prevent the orphaned row from actually being written (the "not silently-orphaned" half of the promise holds), so this is not a data-integrity bug. It is a contract/error-hygiene bug: the specific, explicit claim in `06_API.md` about *how* the failure surfaces is false, and the failure mode that actually occurs is worse from an information-hygiene standpoint (a whole SQL statement plus content values, versus a one-line "project not found").
- **Pre-existing, not introduced by Milestone 2** — the REST route (`api/routes/notes.py::create_note`) has the identical gap; it calls `service.create_note(session, body)` with no project-existence check either. This is not a new regression Milestone 2 introduced. What *is* Milestone 2's responsibility is `06_API.md`'s specific, affirmative claim that the MCP tool behaves differently (cleanly) on this exact input — a claim that was written into the contract without being verified against actual behavior.
- **No test exists for this at all.** Neither `test_mcp_tools_crud.py` nor any other Milestone 2 test calls any create/update tool with an invalid `project_id`. `VERIFICATION_CONTRACT.md` checks AC9 (project scoping) `[x]` without this negative case ever being exercised.
- **Suggested fix:** either add an explicit `projects_service.get_project(session, project_id)` existence check at the top of `create_note`/`update_note`/`create_document`/`update_document` (or a lighter-weight existence-only lookup) before the insert/update, translating a miss into `NotFoundError`, or — if that's judged out of Milestone 2's scope as a REST-affecting service change — narrow `06_API.md`'s claim to match actual behavior and file the REST-layer gap as a separate, explicitly-scoped follow-up rather than leaving a false contract claim in the shipped documentation.

## 4. Original release recommendation (first pass — superseded by §5/§6)

Milestone 2's central architectural commitments hold up well under adversarial pressure: service-layer reuse is genuine (no ORM bypass exists anywhere in the tool handlers, verified by direct code reading, not just by the static check that's supposed to catch it), scope enforcement is real and unconditional for all 12 tools, the corrected delete sequence and orphan-link purge are correctly implemented and ordered for both Notes and Documents, the audit-logging dedup design is genuinely artifact-free (no double-logging anywhere), and the update-logging asymmetry the implementer flagged as a "verified, not assumed" finding is in fact verified — I independently confirmed it against the pre-Phase-11 baseline myself.

However, this is the first milestone where the system can destroy real user data, and the one safety control the entire milestone is built around — "`confirm: true` is structural only, never inferred from anything but the literal field" — does not actually hold: five different non-boolean values (`"true"`, `"True"`, `"1"`, `"yes"`, `1`) all silently authorize a permanent, irreversible delete through ordinary Pydantic type coercion, which is precisely the class of soft/inferred signal the spec's own language says must be structurally impossible. This is a Blocker, not a Major, specifically because it undermines the one guarantee this milestone's own risk framing (`IMPLEMENT.md`: "the first milestone where the system can create, modify, and destroy real persistent user data through MCP") says must not be allowed to fail quietly. The two Major findings (the false "not-found" error contract for bad `project_id`, and the undocumented `default_provider`/`default_model` output leak) are real contract violations worth fixing but do not compromise the authorization/deletion safety model itself.

**Milestone 3 should not be authorized until B1 is fixed** (constrain `confirm` to genuinely reject non-literal-boolean input, with a regression test proving the five coerced values above are now rejected) **and re-verified independently** — this is squarely a Milestone 2 fix (one tool-signature change in two files plus a test), not scope creep into Milestone 3. The two Major findings should be fixed or the documentation corrected to match actual behavior in the same repair pass, since they involve the same files already being touched for B1 and the same "verify claims against actual code" discipline this milestone's own process is built on. The Minor findings are worth a look but do not need to gate re-verification.

### B1 (BLOCKER — `confirm` type coercion): confirmed fixed

  ```
  confirm='true'  (str)   -> isError=True  (Pydantic bool_type validation error) -> note still exists: True
  confirm=1       (int)   -> isError=True  (Pydantic bool_type validation error) -> note still exists: True

  confirm='yes'   (str)   -> isError=True  (Pydantic bool_type validation error) -> note still exists: True
  confirm=1.0     (float) -> isError=True  (Pydantic bool_type validation error) -> note still exists: True

  confirm=False   (bool)  -> isError=True  ("Deletion requires confirm: true...") -> note still exists: True
  ```
