### MAJOR

**M1 — The regression test that is supposed to adversarially prove AC10/AC12 (forge_search never leaks Secret data) never actually creates a Secret. The live behavior is correct — independently re-verified with a real Secret — but the test, and every document citing it, overclaim what was checked.**

- **File:** `backend/tests/test_mcp_tools_search_context.py::test_forge_search_never_returns_secret_data` (lines 147–159).
- **What the test actually does:** creates a `Note` titled `"unrelated"` with content `"unique-narwhal note"`, searches for `"unique-narwhal"`, and asserts each result has `type in ("note", "document")` and no `"secret"` key. **No `Secret` model instance is ever created anywhere in this test file** — confirmed by reading the whole file and grepping it (and `test_mcp_authz_matrix.py`/`test_mcp_audit_completeness.py`, the other two candidate places) for `SecretCreateIn`/`create_secret`/`/api/secrets/secrets` — zero hits across all MCP test files. The only place in the entire backend test suite that creates a real Secret is the unrelated, pre-existing `test_projects_api.py`.
- **What every downstream document claims was checked:**
  - The test's own docstring: *"Adversarial: a Secret whose name matches the query term must not leak into the output even though a plaintext-search-everything implementation would have found it."*
  - `08_ACCEPTANCE.md` AC12: *"a query matching a real secret's name."*
  - `reviews/AGENTIC_REVIEW_M3.md` §1: *"AC12 test — assert no Secret data in output even with a crafted query matching a real secret's name"* and §3: *"AC10/Secrets exclusion holds structurally for the new files"* (this half is true and is the real protection — see below) — but the review's own Milestone 3 task instructions explicitly required this gate to *"independently re-verify AC10/AC12... checked adversarially, not just by re-running the same test the implementer wrote"*, and the M3 review's own text describes the test as adversarial with a real Secret without having apparently noticed it doesn't create one.
  - `09_IMPLEMENTATION_TASKS.md` M3-T1: *"AC12 test — assert no Secret data in output even with a crafted query matching a real secret's name."*
- **Why this matters even though the live property holds.** The actual protection is structural and real: `forge_search` calls `notes_service.search_notes`/`documents_service.search_documents` directly and never imports `services.secrets` anywhere in `search.py` (confirmed by grep, and by the recursive static check in `test_mcp_tools_static_checks.py`). I independently created a real `Secret` (`POST /api/secrets/secrets`, name `"rc-probe-unique-secretname-zephyr"`) and confirmed `forge_search` for that exact name returns zero results referencing it — **the current, live behavior is correct.** But the *test-level* safety net for this specific property is weaker than five separate documents say it is: the static import-boundary check is a **per-file substring match**, not a transitive import-graph check — if a future change made `forge_search` delegate to `search_service.global_search()` (the exact regression `01_SPEC.md` §5.1 explicitly warns against), the offending file would need to import `app.services.search`, not `services.secrets` directly, so the static check would not catch it. And because the shipped "adversarial" test never creates a real Secret, that regression would produce **zero new Secret-typed results** for its own query term (there being no Secret to find) and the test would keep passing — a false green on exactly the property it claims to protect.
- **Severity reasoning.** Not a BLOCKER: no live exploit exists today, and I proved that myself with a fresh, real Secret against the actual shipped code. It is a MAJOR because it is precisely the "contract inconsistencies" / documentation-vs-reality failure class `09_IMPLEMENTATION_TASKS.md` §0 names as something every one of this phase's gates must catch, it recurs across five separate documents (not one typo), and it is a real, actionable gap in the regression-test safety net for the single most security-sensitive property this entire phase is built around (excluding Secrets). This is exactly the kind of thing a final, whole-phase RC audit exists to surface — a gap that survived Milestone 3's own Agentic Review, Milestone 5's "full regression + security suite," and four subsequent documents repeating the overclaim without anyone re-reading the test body.
- **Suggested fix:** add a real `Secret` (via `secrets_service.create_secret` or `POST /api/secrets/secrets`) with a name matching the search query inside `test_forge_search_never_returns_secret_data`, and assert it never appears in `forge_search`'s output (by ID, not just by shape) — mirroring the pattern I used in my own probe. Consider also broadening `test_mcp_tools_static_checks.py`'s `_FORBIDDEN_IMPORTS` substring check into a real AST-based transitive-import check (the still-open, previously-accepted-as-low-priority `m5` finding from `AGENTIC_REVIEW_M2.md` §2) — the two gaps compound each other, and fixing the test alone (recommended as the minimum required fix) closes the coverage gap even if the static check stays substring-based.
