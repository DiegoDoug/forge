### MAJOR

**M1 — `06_API.md` §5's resource contract table states `forge://projects`'s Auth as `forge:read`, but this is empirically false, and `06_API.md` itself (unlike `01_SPEC.md`, `VERIFICATION_CONTRACT.md`, and `resources.py`'s own docstring) was never corrected to say so.**

- **File:** `forge-docs/implementation/Phase-11-Claude-MCP/06_API.md`, §5 table, row `forge://projects` — `| Auth | forge:read |`, with no footnote, caveat, or asterisk anywhere in the document.
- **Empirically confirmed false**: live probe (§1, item 2) — a token holding only `forge:write` (deliberately no `forge:read`) reads `forge://projects` successfully, full data, no error. The equivalent tool, `forge_list_projects`, correctly rejects the identical token. `06_API.md` is the phase's own stated "this is the API this phase ships" document (its own purpose line: *"this is the 'API' this phase ships, in the sense `06_API.md` normally documents REST endpoints"*), and on this specific point it currently promises a protection guarantee that does not exist.
- **This is exactly the "contract inconsistencies" failure class `09_IMPLEMENTATION_TASKS.md` §0 names as something this gate must catch.** The implementer did the hard, honest part — discovered the SDK limitation, verified it by reading SDK source three times over (independently reconfirmed by this review, §1), and documented it thoroughly in `resources.py`'s module docstring, `VERIFICATION_CONTRACT.md` §6/§10, and `CURRENT_STATE.md` §5. But of the four places a reader might reasonably look to learn "does this resource actually enforce scope," the one that's supposed to be the authoritative contract (`06_API.md`) is the one place still stating the wrong answer. This is the same class of gap Milestone 3's Agentic Review found for its own AC18 claim (a correction made in three docs but not a fourth) — here it recurs in the opposite direction (three docs corrected, the primary contract doc missed).
- **My independent judgment on the underlying technical/security question the implementer flagged** (not just the doc gap): the SDK constraint is genuine — confirmed by reading `mcp/server/mcpserver/server.py`'s `MCPServer.resource()` decorator and `resources/types.py`'s `FunctionResource.fn` directly (§1) — and there is no viable in-SDK workaround (no `ContextVar`-based side channel exists anywhere in the installed package). Reshaping the resource into a template to force `Context` injection would move it off `resources/list` and break `06_API.md` §5's own explicit "auto-discovery: yes" requirement for this exact resource — a worse trade. Given (a) the exposed data is genuinely low-sensitivity (project name/description/color/counts; `secret_count` is already excluded at the `project_to_mcp_out` level, so vault size never leaks), (b) connection-level authentication (a valid, non-revoked token) is still fully enforced by `McpBearerAuthMiddleware` for this request like every other, and (c) `01_SPEC.md`'s own stated threat model for this phase is explicitly "one operator, one master key" — a single trust boundary, not a multi-tenant system where one token's holder is meant to be isolated from another's — I judge this an **acceptable narrow exception**, not a BLOCKER and not something that should force dropping the resource to template-only. It does not meet BLOCKER's security bar ("bypasses auth" — authentication is intact; only one specific, low-sensitivity resource's finer-grained scope check is structurally unenforceable) given this phase's own accepted threat model.
- **Required fix, narrow and mechanical**: correct `06_API.md` §5's table (e.g. footnote or an explicit "not enforced — SDK limitation, see `app/mcp/resources.py`" note on that one cell) so the phase's authoritative API contract states the true, current behavior. This is a documentation-only fix — no code or test change needed, no re-architecture — but it must land before this milestone can be called done, matching Milestone 3's own precedent that a contract document stating something false is itself a MAJOR finding independent of whether the underlying behavior is judged acceptable.

### MINOR

**m1 — Resource-read errors surface as a generic, unclassified SDK-level internal error, not the clean not-found message the equivalent tool gives.**

- **Empirically confirmed**: `forge://projects/does-not-exist` and `forge://projects/{a real note ID}` both return `{"error": {"code": -32603, "message": "Error creating resource from template forge://projects/<id>", ...}}` over the wire. The equivalent tool, `forge_get_project` with the same bad ID, returns a clean `"Error executing tool forge_get_project: Project not found"`.
- **Traced to the SDK, not Forge's code**: `mcp/server/mcpserver/server.py::MCPServer.read_resource()` explicitly does `except MCPError: raise` / `except Exception as exc: ... raise ResourceError(f"Error reading resource {uri}") from exc`, with the SDK's own comment stating *"we should not leak the exception to the client"* — a deliberate, blanket behavior for every non-`MCPError` exception a resource function raises, not a bug introduced this milestone.
- **Why it's still worth a MINOR, not a shrug**: a genuine not-found (expected, benign) and a genuine internal bug (e.g. a DB error) are currently indistinguishable to a calling Claude session for either resource — both produce the identical `-32603` shape. `test_mcp_resources.py::test_forge_project_resource_unknown_id_errors` only asserts `"error" in body`, which would pass identically in either case — a real coverage gap on top of the UX gap, since a regression that turned a clean not-found into a genuine crash would not be caught by this test.
- **Avoidable, if ever prioritized**: catching `NotFoundError` inside `forge_project_resource` and re-raising it as `mcp.shared.exceptions.McpError` (with an appropriate code/message) would pass through the SDK's `except MCPError: raise` branch unmolested, giving resources the same error quality tools already have — this is not a dead end the way the scope-enforcement limitation is.
- **Not blocking**: no security or data-integrity impact, and the resource layer degrades safely (a clean protocol-level error, not a crash or a leaked traceback) either way. Backlog-appropriate per `12_BUG_CLASSIFICATION.md` §2's MINOR bucket ("validation asymmetry with no real-world reachable failure mode" beyond message clarity).
