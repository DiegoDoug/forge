# Phase 11 — Acceptance Criteria

> **Purpose:** Objective, checkable acceptance criteria for Phase 11.
> **Status:** All 20 criteria checked off below, 2026-08-20, against actual test/review evidence at the human review gate's own request — not inferred from a summary. Each line cites the specific test(s)/live-probe(s) that satisfy it. Awaiting owner sign-off as part of the mandatory human review gate (`IMPLEMENT.md`).
> **Last Updated:** 2026-08-20

## 1. Connectivity & auth

- [x] AC1 — Given `FORGE_MCP_ENABLED=true` and a **persistent** MCP token provisioned via `POST /api/mcp/tokens`, Claude Code can connect to `/mcp` via Streamable HTTP using `claude mcp add --transport http`. (Corrected: "bootstrap or issued" was the original wording; per owner review, the bootstrap token must never be Claude's connection credential — see AC1a.) — Verified against a real `docker compose up --build` production stack in Milestone 5 (`initialize` → `tools/list` (18/18) → `resources/list` through nginx, with a token provisioned via the real REST route).
- [x] AC1a — Given the raw bootstrap token (`FORGE_MCP_BOOTSTRAP_TOKEN`), presenting it directly to `/mcp` (any tool, any resource) is rejected exactly as if no credential were presented — the bootstrap token authenticates `POST /api/mcp/tokens` only, never `/mcp` itself. — `test_mcp_server.py::test_bootstrap_token_is_never_accepted_by_mcp_itself`; re-confirmed live by both the Milestone 4 and Milestone 5 (whole-phase) Agentic Reviews and in the Milestone 5 Docker verification (401, same as no credential).
- [x] AC1b — `POST /api/mcp/tokens`, authenticated with a valid bootstrap token, creates a persistent `McpToken` and returns the raw value exactly once; a subsequent `GET /api/mcp/tokens` for that token never returns the raw value, only metadata (id/name/scopes/timestamps). — `schemas/mcp_tokens.py::McpTokenOut` structurally has no `token` field (only `McpTokenCreatedOut`, returned once, does); verified live via the Settings-page UI in Milestone 5 and by `test_mcp_tokens_api.py`.
- [x] AC1c — Given `mcp_bootstrap_enabled=false`, `POST /api/mcp/tokens` rejects even a correct bootstrap token — the config flag is a true kill switch, checked before the token comparison. — `require_bootstrap_auth` checks `mcp_bootstrap_enabled` before any token comparison; re-confirmed live by the Milestone 5 Agentic RC Review.
- [x] AC2 — Given `FORGE_MCP_ENABLED=false` (default), `/mcp` is unreachable through both direct backend access and the nginx proxy. — `test_mcp_server.py::test_mcp_disabled_by_default_leaves_mcp_unmounted` (404, `/health`/`/api/*` unaffected).
- [x] AC3 — Given a missing or malformed `Authorization` header, every `/mcp` tool call is rejected before any service/DB access occurs. — `test_mcp_server.py::test_missing_authorization_header_is_rejected_before_any_protocol_processing`, `test_malformed_authorization_header_is_rejected` (401 at the ASGI-middleware layer, before the MCP SDK's own dispatch).
- [x] AC4 — Given a revoked persistent MCP token, the connection can no longer perform any protected operation, immediately (no caching delay). — `test_mcp_server.py::test_revoked_token_is_rejected_immediately`; re-confirmed live (full lifecycle: provision → use → revoke → immediate 401) by the Milestone 5 Agentic RC Review's own probe.
- [x] AC4a — `last_used_at` is updated at most once per 5-minute window per token under repeated/rapid tool calls (write-throttling behavior, not an update on every request) — verified by call count vs. write count, not merely by the field eventually being non-null. — `test_mcp_tokens_service.py::test_touch_last_used_is_throttled_within_the_five_minute_window` (two calls, one write) and `test_touch_last_used_updates_again_once_the_throttle_window_has_passed` (backdated timestamp, confirms it does eventually update).
- [x] AC5 — Given a token with only `forge:read`, any write or delete tool call is rejected with the underlying data provably unchanged. — Generalized to all 18 tools/all 3 scopes in Milestone 5's `test_mcp_authz_matrix.py` (57 parametrized cases plus a DB-level mutation-safety check across every wrongly-scoped write/delete tool).

## 2. Knowledge CRUD

- [x] AC6 — Given `forge:write`, Claude can create, read (full content), and update Notes and Documents through MCP tools, and the resulting rows are indistinguishable in the database from ones created via the REST API (same schema, same `ActivityLog` pattern except `source="mcp"`). — `test_mcp_tools_crud.py` (Milestone 2); audit-shape re-confirmed by Milestone 5's `test_mcp_audit_completeness.py`.
- [x] AC7 — Given `forge:delete` and `confirm: true`, Claude can delete a Note or Document, and its `knowledge_links` rows are purged (no orphans left behind). — `test_mcp_tools_crud.py`'s orphan-link regression guard (Milestone 2); sequence re-read and re-confirmed unregressed by the Milestone 5 whole-phase review.
- [x] AC7a — A delete call against a nonexistent `note_id`/`document_id` (with valid `confirm: true`) returns a not-found error and stages **zero** database changes — verified by asserting no `knowledge_links` rows are touched for an ID that never existed, proving the existence check runs before link purging, not after or concurrently. — `test_delete_nonexistent_note_stages_zero_changes` and its Document-side symmetric test (Milestone 2).
- [x] AC8 — Given `forge:delete` but `confirm` omitted or `false`, the delete tool call fails validation and nothing is deleted. No natural-language phrasing in surrounding context (which the MCP server cannot see regardless) can substitute for the literal structured field. — `test_delete_note_rejects_non_boolean_confirm_values` (the Milestone 2 Agentic Review's BLOCKER fix — `StrictBool`, not `bool` — and its dedicated regression test); re-confirmed live (with `confirm: true`, without) by the Milestone 5 whole-phase review.
- [x] AC9 — Given `forge:write`, Claude can create/update Projects, and Notes/Documents can be scoped to a project via MCP the same way the UI scopes them. — `test_mcp_tools_crud.py` (Milestone 2).
- [x] AC10 — No MCP tool exposes `Secret` data, `secret_count`, or any crypto-service primitive, under any scope combination including a token that (mistakenly or maliciously) carries `forge:secrets`. — Structural: zero references to `services.secrets`/`services.crypto` anywhere in `app/mcp/**` (`test_mcp_tools_static_checks.py`, recursive, re-confirmed by grep at every milestone including the Milestone 5 whole-phase review). `forge:secrets` grants nothing — no tool's `require_scope` call ever checks for it, so a token holding only that scope is rejected by every tool exactly like a zero-scope token (covered by `test_mcp_authz_matrix.py`'s zero-scope sweep, since the two are functionally identical from every tool's point of view).

## 3. Search & context

- [x] AC11 — Given a project, `forge_context` returns the project record, matching Notes/Documents, their tags, and their existing links — every field returned is backed by an existing Forge query (no fabricated/synthetic field). — `test_forge_context_aggregates_project_notes_documents_tags_links` (Milestone 3).
- [x] AC12 — `forge_search` never returns Secret names or metadata, even though the underlying `search_service.global_search` (which this tool deliberately does not call) does include them for the REST API's own `/api/search`. — `test_forge_search_never_returns_secret_data`, **repaired 2026-08-20**: the shipped Milestone-3 version never actually created a `Secret` row (a real MAJOR finding from Milestone 5's whole-phase Agentic RC Review, independently re-verified after the fix) — it now inserts a real `Secret` and asserts it never appears in output by content. The underlying product behavior was never actually broken (structural exclusion — `search.py` never imports `services.secrets`; the reviewer independently proved this live with a real Secret before the test itself was fixed), but the regression test's own coverage gap is now closed.
- [x] AC13 — An invalid `project_id` passed to `forge_context` produces an explicit error, not silently-unfiltered results. — `test_forge_context_invalid_project_id_errors_not_silently_unfiltered` (Milestone 3).
- [x] AC13a — Given a project with more matching Notes/Documents for a topic than the 50-per-type cap, `forge_context`/`forge_search` with `project_id` set returns results constrained to that project from the query itself — verified by a project containing >50 matching items across both types where an unscoped-then-filtered implementation would provably drop relevant results the query-scoped implementation does not. — `test_forge_search_project_scoping_is_query_level_not_post_filtered`; the Milestone 3 Agentic Review independently reproduced the rejected naive implementation by hand and confirmed it returns 0/30 where the shipped one returns 30/30.
- [x] AC13b — `forge_context`'s link lookup issues a bounded, small number of queries regardless of result-set size (one batch query via `list_links_for_items`, not one per matched item) — verified by query-count assertion at, e.g., 50+50 matched items, not merely by correct output. — `test_knowledge_service.py::test_list_links_for_items_issues_a_bounded_query_count_regardless_of_item_count`.

## 4. Memory workflows

- [x] AC14 — A decision captured via `forge_capture_decision` in one Claude session is retrievable via `forge_search`/`forge_context` in a later, independent Claude session (proves cross-session continuity end-to-end, not just that the write succeeded). — **Verified live at three independently-increasing levels of rigor, not merely asserted**: (1) `test_mcp_memory_continuity.py`'s two tests (Milestone 4) — a fresh persistent token AND a fresh `initialize` handshake for the "later session" half; (2) the Milestone 4 Agentic Review's own stronger probe — a second, fully independently-rebuilt `app`/engine instance (fresh `get_settings`/`get_engine`/`get_sessionmaker` caches), not just a second token on the same app object; (3) the Milestone 5 whole-phase RC Review independently reproduced (2) again at the final gate, with cache-clearing between sessions specifically to rule out any in-process shortcut. All three held.
- [x] AC15 — Captured session/decision notes carry the reserved tag (`ai-decision`/`ai-session`) and are otherwise ordinary Notes — visible in the existing Notes board and Knowledge Hub UI with no special-casing required there. — `test_mcp_tools_memory.py` (tag applied, reused across calls via the existing `add_tag` create-or-reuse contract); discoverability re-proven by AC14's own continuity tests using ordinary `forge_search`/`forge_context`, no dedicated memory-retrieval tool.

## 5. Regression, audit, deployment

- [x] AC16 — Existing Forge REST APIs (`/api/*`) behave unchanged — full existing backend test suite remains green. — 469/469 as of Milestone 5 (arithmetic independently re-derived by the Milestone 5 Agentic RC Review via summed `--collect-only` counts, not just "exit 0"); zero changes under `app/api/`, `app/services/{notes,documents,projects,knowledge}/`, `app/models/` this milestone.
- [x] AC17 — Existing Forge tests remain green after this phase's migration is applied (up/down/up). — Verified in Milestone 1; no further migration since (Milestone 4's memory capture and Milestone 5's token UI both needed zero schema changes).
- [x] AC18 — Production Docker deployment exposes `/mcp` correctly through nginx when enabled, and every MCP-originated **create and delete** mutation appears in `ActivityLog` with `source="mcp"`, **exactly once per mutation** — not two. **Note/Document updates and knowledge-graph link create/delete are documented exceptions** (see Open Questions below) producing zero `ActivityLog` rows, matching pre-existing REST behavior exactly; `forge_update_project` does log. — Docker: a full, isolated `docker compose -p forge-m5-verify up --build` run in Milestone 5 (health, setup, token provisioning, full MCP handshake through nginx, torn down cleanly). Audit: Milestone 5's `test_mcp_audit_completeness.py` — all 5 create-tools + `forge_update_project` log exactly once with `source="mcp"`; both delete tools log exactly once; the three documented no-log exceptions (`forge_update_note`/`forge_update_document`/`forge_link_items`/`forge_unlink_items`) confirmed to produce zero rows; all 6 read tools confirmed to write nothing.
- [x] AC19 — A `forge_session` browser cookie cannot authenticate to `/mcp`, and an MCP bearer token cannot authenticate to `/api/*` — the two auth schemes are provably independent. — `test_mcp_server.py::test_mcp_token_cannot_authenticate_against_the_rest_api`, `test_browser_session_cookie_cannot_authenticate_against_mcp`; re-verified live in both directions by the Milestone 5 whole-phase review (which caught and corrected a leftover-cookie confound in its own first probe attempt before confirming the correct result).
- [x] AC20 — No MCP tool handler contains a direct `session.get(<Model>, ...)` or equivalent raw-ORM call — every tool reaches data exclusively through a `services/*` function (static/import-graph check across `backend/app/mcp/tools/**`, not just a code-review spot-check). — `test_mcp_tools_static_checks.py::test_no_mcp_module_calls_the_orm_directly`, recursive over all of `app/mcp/**`, unchanged since Milestone 2 and re-confirmed passing at every subsequent milestone including Milestone 5.

## 6. Open questions requiring a human decision (not resolved by this planning session)

- [x] **Resolved by the owner, 2026-08-20**: Milestone 5 builds a Settings-page UI (not an admin script) wrapping `POST/GET/DELETE /api/mcp/tokens` — list active tokens with scopes/created/last-used, provision a new one (shows the raw token exactly once, per §4.3.1's contract), revoke with a named confirm dialog. No backend change was needed: the existing REST routes already accept `AuthDep` (browser session) per `01_SPEC.md` §4.3.1, so this was purely a frontend addition (`frontend/features/mcp-tokens/`), wired into the existing Settings page. (`01_SPEC.md` §4.6)
- [ ] **New, found during Milestone 2 implementation**: should `notes_service.update_note`/`documents_service.update_document` gain `ActivityLog` logging (matching `update_project`'s existing behavior) as a deliberate REST-facing feature improvement in a future phase, or is the current asymmetry (Project updates logged, Note/Document updates not) an acceptable, pre-existing product characteristic Phase 11 should simply preserve rather than "fix" as an unplanned side effect? Not decided by this implementation session — changing it would alter existing UI-facing behavior (every note/document edit would start appearing in Recent Activity) and needs an explicit product decision, not an incidental one made while wiring `source="mcp"` through. (`01_SPEC.md` §4.5)
- [ ] Should `forge_delete_project` be added in a later phase, and if so, does Projects need a "confirm cascade" pattern given it currently *unscopes* rather than deletes children? (Out of scope for Phase 11 as specified.)
- [ ] Is OAuth 2.0 worth building for MCP auth in a future hardening phase, or does the static bearer-token model remain the long-term answer for a self-hosted single-tenant tool? (`01_SPEC.md` §2)
- [ ] Should ADR-0008 (Capability Registry) be promoted from Proposed to Accepted using MCP tools as its second concrete use case, or is the flat tool-registry dict in `app/mcp/tools/__init__.py` sufficient indefinitely? (`01_SPEC.md` §7)
- [ ] Should reads (`forge_search`, `forge_context`, `forge_get_*`) be logged to `ActivityLog` at all, given the existing UI/REST layer has never logged `viewed` actions either — is this consistency worth preserving, or does an AI-driven read deserve visibility the UI's own reads never got? (`01_SPEC.md` §4.5)
- [ ] **New, found during Milestone 3 implementation (Agentic Review)**: should `knowledge_service.create_link`/`delete_link` gain `ActivityLog` logging (matching `create_note`/`delete_note`'s existing behavior) as a deliberate REST-facing feature improvement in a future phase? Unlike a single note's title edit, a knowledge-graph mutation changes the *relationships* between pieces of knowledge — arguably a case where audit visibility has more product value than the update_note/update_document asymmetry this section already tracks, precisely because it's the kind of low-visibility, easy-to-do-repeatedly action `01_SPEC.md` §7's ADR-0004 reconciliation argument ("every MCP write is scoped, token-gated, audited") depends on holding true. Not decided by this implementation session — changing it would alter existing REST-facing behavior (every link create/delete would start appearing in Recent Activity) for every caller, not just MCP ones. (`01_SPEC.md` §4.5)
