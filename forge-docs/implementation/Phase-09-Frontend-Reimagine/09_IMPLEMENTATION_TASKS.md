## 1. Shape of this breakdown

33 tasks (T0, T0.5, T0.6, T1–T30) across six milestones. Larger than any prior Forge phase because it touches all 17 routes; each individual task is small.

Ordering follows dependency, then visual priority, then risk, with one addition made after the graph existed:

- **T0.5 fixes the two verified defects before any design work.** The font defect distorted every prior sizing and density judgement in the product's history; correcting it first means the redesign's decisions are made against real metrics. See the Milestone 0 note.
- **T1 is deliberately alone**: a single global CSS change affecting all 40 primitives simultaneously — the highest-risk task and the one everything else depends on. Verified before any screen work begins.
- **Migration order was re-checked against [`11_SCREEN_GRAPH.md`](11_SCREEN_GRAPH.md) §6** and needed no resequencing. Two coupled clusters (`workbench↔notes↔projects`, `projects↔model-playground`, `notes↔knowledge`) gained explicit re-verification requirements instead.

**Every task carries a "Preserve" line.** That line is the contract — it names what must still be true after the task, and it is what [`08_ACCEPTANCE.md`](08_ACCEPTANCE.md) re-tests. A task whose visual work is done but whose Preserve line is unverified is **not** done.

Checkpoint triggers per [`../../10_CHECKPOINT_PROTOCOL.md`](../../10_CHECKPOINT_PROTOCOL.md) §1: every milestone boundary, every 10–12 tasks, ~70% context, and any blocking architectural decision.

The design-side mirror of this list is [`TASKS.md`](../../../.design/frontend-reimagine/TASKS.md). Where the two disagree, **this document wins**.

## 2. Milestone 0 — Baseline and foundation defects

> **Why T0.5 exists as its own step, before the design system.** Raised by the project owner, 2026-08-06, and it is the sharper framing: the font defect is not a cosmetic bug to be fixed *as part of* the token work. **Every spacing, density, truncation, wrapping, button-sizing, and table-rhythm judgement in Forge's entire history was made while the application rendered in the wrong typeface.** Geist and Times New Roman have different metrics — different x-height, width, and vertical rhythm. So every downstream design decision in this phase must be made *after* the correct typeface is in place, or it inherits the same distortion.
>
> Same logic, smaller stakes, for `/system/status`: a screen with a permanently-missing data row cannot be judged as a layout.
